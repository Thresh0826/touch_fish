# 冷启动的响应等待与部门状态观察

用户确认现场根因：冷启动时WDMS登录窗口的UI线程长时间不处理消息；09:27的成功轮次窗口已就绪，三部门已激活，因此没有进入标签点击分支。本轮将窗口响应作为部门状态观察的前提，为较慢电脑保留启动余量。

当前工作流`one-click-steps-v7.4-startup-ready`，登录`department-settle-home-markers-v9-startup-ready`。基线b1c8c59a，源码版本以本包SOURCE_MANIFEST.json为准。

- 窗口出现后，先验证身份和可见状态，使用一次只读WM_NULL探活；成功响应连续2秒后才扫描登录控件。
- 首次部门等待每轮先探活，再读取原有三个下拉框的可用状态。探活失败时暂停状态读取，清除此前稳定计时；恢复响应后重新观察至少5秒、连续稳定2秒。
- 控件扫描前的就绪检查与首次部门观察共用窗口出现后90秒期限，不分别追加90秒。正常就绪窗口按稳定条件继续，90秒是上限。
- 补选后的状态稳定等待和填写前最终确认也要求窗口能响应，仍使用原来的30秒阶段上限。
- 启动卡顿只对WDMS_UNRESPONSIVE/WDMS_HEALTH_CHECK_FAILED做只读等待；权限拒绝、窗口身份变化及其他错误立即停止。期限到仍不响应报LOGIN_WINDOW_NOT_READY，未绕过失败继续操作。

点击仍使用原先一次WM_LBUTTONDOWN/UP；未选中判定仍使用对应下拉框IsWindowEnabled，已选中仍保留。与b1c8c59a比较，点击实现、部门标签映射、选中函数的AST完全相同，core/query_policy.py字节相同；本轮没有再调整消息等待上限，也没有重发点击或切换点击方式。

新增11项回归，覆盖卡顿22秒后恢复、缓存状态不提前判断、就绪前不点击、持续不响应90秒停止、再次卡顿重置计时、权限拒绝、探活跨越期限、共享启动期限、快速已就绪路径、一次探活不嵌套15秒重试、身份变化及真实child调用顺序。三个实际行为场景对b1c8c59a原代码均失败，新版通过；源码全量431项通过，84模块静态门禁无发现，仍有两条既有管道ResourceWarning。

用户在Windows正常退出WDMS后，使用完整新包冷启动，先前三个货主；现场效果依本轮日志和库存人工核对确认。窗口不响应期间不操作键鼠。失败停止并回传本轮flow.jsonl、login目录JSONL及对应console；只交接允许内容。Windows实机未由桌面助手执行，windows_verified保持false。
